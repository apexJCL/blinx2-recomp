## Context

- The one-CPU gate (`s_dispatch_gate`, `kernel_hal.c`) stands in for "the processor is at DISPATCH". A guest thread takes it in `irql_track_gated` on its raise and gives it back on the lower that leaves DISPATCH; the timer thread's `kernel_drain_dpcs` takes it with TryEnter around each DPC; device models deliver ISRs under it or post them to the holder (`xbox_IrqPost`), and the holder runs posted routines at safe points (`xbox_IrqSafePoint`: kernel thunk entry, spin-wait yield, the release in `irql_track_gated` and `irq_release_point`). `irq_run_line` saves and restores the holder's guest registers around a routine (`irq_regs_save`/`irq_regs_restore`), switches `g_esp` to a worker stack slice and brackets the IRQL with `xbox_IrqlEnterInterrupt(16)`.
- DPCs: `bridge_KeInsertQueueDpc` appends `{dpc, arg1, arg2}` to `g_dpc_queue` under `g_dpc_lock` and sets the KDPC's `Inserted` byte; `kernel_drain_dpcs` (timer thread only) pops under the lock, clears the byte before the routine, and runs it through `kernel_run_dpc`, which pushes the four arguments on `g_esp` and calls the routine at DISPATCH through `xbox_IrqlEnterInterrupt(2)`. The timer thread sleeps in `xbox_HostSleepNs` (nanosleep; a high-resolution waitable timer on Windows) to the earliest of the next vblank edge, the next kernel timer and 10 ms; a drain that found the gate busy shortens the next sleep to 1 ms.
- Threads that run guest code: guest-main (`host_main`, the first `PsCreateSystemThreadEx` call runs inline) and the spawned workers (`bridge_thread_main`), each with its own guest stack and TIB. The timer thread, the vblank-ack thread, the APU frame thread and the OHCI thread have worker stack slices and TIBs for the routines they run but no guest context of their own.
- Evidence: `runs/m1hang/findings.md`. The DPC's loop in `sub_003346BE` has no thunk call (the pending APU line was never taken: 1298 wait logs), the stop-list head and the self-linked node, the voice's re-activated state, and the runtime counters that exclude an ungated delivery.

## Decisions

1. **The drain runs on the guest thread that crosses DISPATCH, holding the gate.** On the console a DPC queued by an ISR runs when the processor's IRQL drops below DISPATCH, on whatever stack the interrupted thread had, before that thread resumes. The faithful model here is: whichever guest thread next owns "the processor at DISPATCH" runs the queue. Two places own it: the raise (a guest thread that just took the gate, at DISPATCH; the DPC runs before the caller's critical region starts, which is exactly where Play would otherwise find the stop list undrained) and the release point (a guest thread giving the gate back after a hold, after it has run the posted interrupts, which is the ISR-exit path when the ISR was posted to this holder). Both already exist as safe points. Both drain with the thread's own guest stack (`g_esp` below the caller's frame, as `kernel_run_dpc` already does for the timer thread's slice) and with the full register save and restore `irq_run_line` uses, since the raise thunk has read its arguments by then and the bridge writes `g_eax` after. The DPC runs at DISPATCH: at the raise the level is already 2, so `kernel_run_dpc`'s own `xbox_IrqlEnterInterrupt(2)` is a no-op; at the release point it raises and lowers inside the gate the release point took with TryEnter.
2. **Only guest threads drain.** A thread-local mark set by `xbox_log_thread_role` for `guest-main` and `guest-worker`. The timer thread keeps its own drain. Device-model threads deliver under the gate and leave: the DSOUND DPC may wait on the APU frame thread (a trapped front-end method cleared by `se_frame`), and the OHCI thread has the same shape; a DPC on either would wait on itself. That leaves one window open: an ISR delivered gated on a device-model thread queues a DPC that runs on the next guest raise or the woken timer thread, which for DirectSound is before Play (the raise) in every case.
3. **No nesting.** A thread-local `in_dpc` flag: a DPC's own raises and lowers never start another drain (the queue is being drained already; `kernel_drain_dpcs` on the timer thread is unaffected). A thread inside a posted ISR (`t_in_isr`) never drains: the ISR queues, the exit path drains. A routine that queues itself again is picked up by the same drain loop, as the `Inserted` byte is cleared before it runs.
4. **The timer thread is woken.** `xbox_HostTimerSleepNs` is a wait on a condition variable with a nanosecond deadline (`pthread_cond_timedwait`; a waitable timer plus an event in `WaitForMultipleObjects` on Windows), with a latched wake so a wake that lands before the sleep is not lost. `KeInsertQueueDpc` calls `xbox_HostTimerWake` after the append. The vblank schedule keeps its clock: the deadline is the same instant the nanosleep would have ended at, and an early wake is followed by the usual schedule computation. The busy-gate retry stays at 1 ms (proposal).
5. **`dpc_on_raise=0`** (debug tier, `recomp_env`) disables the guest-thread drains and the wake together, for A/B against the old behaviour on a title where the new ordering changes something. Read once with the irq config and reloaded by `xbox_IrqReloadConfig` for the tests.
6. **Not in this change:** running DPCs on device-model threads (decision 2), a shorter busy retry (decision 4), a linked check in the generated `sub_00335C18` (proposal), a real per-processor DPC queue drained by every lower (every lower would have to take the gate; the raise and the release point cover the console's ordering where it is observable).

7. **A vblank raised while PMC_INTR_EN_0 is masked posts no ISR** (found at the Burnout 3 gate, toolkit e0c4508). With decision 1 the D3D vblank DPC can run on the gate holder itself. The model used to post every vblank to a busy gate's holder and keep `tick_busy` up until the holder's next safe point. While `tick_busy` is up, the vblank-ack thread treats PCRTC_INTR_0's bit as the new vblank, not as the DPC's ack (that is the race it guards). The XDK DPC acks by writing PCRTC_INTR_0 = 1, then spins until PMC_INTR_0's PCRTC bit drops (Burnout 3 `sub_00356DA0`, `loc_00356E50`), and that loop calls no thunk. So a vblank raised during the spin is posted to the very thread that is spinning: the ISR never runs, `tick_busy` never drops, and the ack never comes. It happened in 3 of 3 runs, 380-608 s in. Under the old ordering the DPC ran on the timer thread, which raises the vblanks itself, so no new vblank could arrive during the spin.
   - On hardware the NV2A raises its line only while PMC_INTR_EN_0 is on. The XDK ISR returns FALSE when it is 0, writes 0 before it queues its DPC, and the DPC writes it back last (Burnout 3 `sub_00356AD0`, `sub_00356BF0`).
   - So the raise now reads the enable (`xbox_VblankRaiseBits`). When it is masked, the raise latches the PMC bit, calls and posts nothing, and arms the ack watch the way a declined delivery does.
   - Only one thread raises vblanks, and while one is pending no other is raised. If the raise reads the enable on, the previous DPC has finished, so no DPC can spin before this vblank's ISR has run.
   - The other shapes were set aside:
     - Narrowing the drain (no guest-thread drain of the D3D DPC, or none while an interrupt is pending) would reopen the DirectSound double insert for any DPC on the excluded list, and it treats the symptom.
     - A `spin_waits.json` entry for the loop is per-title, and it would run the declined ISR inside the DPC.
   - **Not the hardware's timing.** The NV2A line is level-triggered: a vblank latched while masked raises the line the moment the DPC writes PMC_INTR_EN_0 back. The model has no write hook on the enable, so the latched bit is merged into the next tick and the ISR sees it up to one frame (16.7 ms) late. The XDK ISR handles a PMC bit that was already up, and the frame clock is unchanged, so this was accepted; an unmask hook is the fix if a title ever counts vblanks across its DPC.
   - **The enable read is a snapshot.** The timer thread reads PMC_INTR_EN_0 while the holder's ISR and DPC write it. A raise that reads it on just before the guest masks it posts the ISR, which then sees the mask and declines, as every masked vblank did before e0c4508. A raise that reads it masked just before the DPC unmasks is latched and merged into the next tick, as above. Neither leaves `tick_busy` up behind a spinning DPC.
   - **The masked arm leaves PCRTC_INTR_0 alone** (Fable review of e0c4508). The masked path first reused the declined path's arm, which also clears PCRTC_INTR_0's vblank bit. On a declined delivery that bit is the tick's own, but a masked tick sets none, so a bit that is up is the DPC's ack. An XDK DPC that writes its ack once and then spins lost it whenever a masked tick landed before the vblank-ack thread took it, and spun, with every guest raise behind it, until the nv2a-ack backstop a second later. The arm is now split (`xbox_VblankArmBits`, `raised` 0 on the masked path), and `tests/vblank_ack` has a write-once-ack DPC that fails without the split.
   - The OHCI and APU posts were checked for the same shape. Their DPCs do not spin on a status bit that only a post-ISR thread clears; the 0x368362 slot in the first stall's stack was a stale return address from an earlier OHCI drain, not a live frame (`runs/m1hang/b3-stall/`).

## Risks / Trade-offs

- **A DPC now runs on a title thread, inside `KfRaiseIrql`.** On the console it ran on whichever thread was interrupted, so a DPC that could deadlock against a title thread's held resource deadlocks there too; DirectSound's DPC skips its critical section at raised IRQL for that reason (`fs:[0x24]`, published by `irql_publish`). A title DPC with a deeper stack than the thread has left is the same risk the console takes. The register save/restore and the `in_dpc` guard keep the raise's own contract (return value, caller's registers) intact.
- **Ordering changes for every title.** Burnout 3's DPCs (vblank callback, DSOUND, USB) run earlier than before. Gates: Burnout 3 boot and vehicle select under Proton (the frame-thread pair), BLiNX 2 goldens on Metal and D3D11, the bomb-door and results-screen repro, `audio_check.py` not required (no mixing change).
- **Vblank pacing.** The timer thread's sleep moves from `nanosleep` to a condition-variable wait with the same absolute deadline; macOS and Linux put both on the same kernel timer, Windows keeps the high-resolution waitable timer. The pacing numbers (flips/s, raster ms) are read on the stage1 golden to confirm nothing moved.
- **Masked vblanks are dropped earlier.** A vblank inside the DPC's mask window used to reach the ISR and be declined; now it is counted as declined without the call. The two differ only for an ISR that ignores PMC_INTR_EN_0, which the XDK's does not. `tests/vblank_ack` pins the rule: a DPC spinning in the XDK loop while a masked vblank is raised is let go, and an unmasked raise still sets `tick_busy` and both bits for the ISR.
- **Tests:** `tests/dpc_order`, standalone against the runtime library like `tests/irq_safe_points`, with events ordering every hand-off: (a) a gated ISR on a model thread queues a DPC; a guest thread's raise runs it before the raise returns, on that thread, at DISPATCH, with its registers back; (b) a guest holder at DISPATCH takes the posted ISR at a safe point, the DPC does not run inside the ISR and runs at the lower that gives the gate back, on the holder; (c) a queued DPC ends the timer thread's sleep within 2 ms (the wake primitive, and `xbox_DpcQueue` calling it); (d) a device-model thread's gated delivery and release never run a queued DPC; the next guest raise does; (e) `dpc_on_raise=0` records the old behaviour. The existing `irq_safe_points`, `kernel_irql_abi`, `spin_wait` and `apu_irq` tests must still pass.
