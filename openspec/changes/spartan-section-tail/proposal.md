## Why

With BLX-132's fence fix, Spartan: Total Warrior (XDK 5849, `spartan/tca`) creates its D3D device, loads its sound banks and render targets, presents one frame and then stops for good in a `KeDelayExecutionThread` loop under `sub_001ADCA0` ← `sub_000DC6E0` (`runs/blx132/r10-proto-mirror`, BLX-134). That loop is not a poll that a missing event or interrupt would release. It is the game's own fatal-error screen, reached because a translated XDK function returns without popping its stack.

The chain, from the stop back to the cause (evidence in `runs/blx134/`, BLX-134 notes in `notes/blx134/` after the merge):

- **The stop is a fatal-error screen.** `sub_001ADCA0` formats `Fatal error on file %s.` (0x2AF9C4), draws it, presents (`sub_0022A290`), then calls `Sleep(1000)` (`sub_001B2B45` → `KeDelayExecutionThread`) forever. Its caller `sub_000DC6E0` is the section lookup: it searches the section table at 0x31A668 (24 entries, all of `data/sections.txt` read correctly) and, on a miss, prints `Couldn't find section '%s' - update your sections.txt - infinite loop in the meantime - Gil` (0x2997D0). The guest stack at the stop holds that string with an **empty** name (`runs/blx134/r1-lldb/attach.txt`).
- **The empty name comes from the front end's exit routine.** The section state machine `sub_000DC750` runs state 4 (exit) through the FE object's vtable slot +0x10, `sub_00182880`, which copies the next-level name from `[FE+0xA4]` and looks it up. `[FE+0xA4]` is 0 at that point (`runs/blx134/r7-exit/lldb.txt`): no FE script `LEVEL` command ever ran (`sub_0017DAB0` was never hit, `runs/blx134/r3-bp`).
- **The FE update reported "done" on its first call.** State 3 calls the FE update `sub_0017F630` until it returns 0, and it returns `[edi+0xA4] == 0 ? 1 : 0`. It was called exactly once, with `[FE+0xA4]` = 0, and the state machine moved to 4 (`runs/blx134/r8-count/lldb.txt`). So the update read `+0xA4` of something that was not the FE object.
- **Its edi was not the FE object.** Reading the guest registers (`g_edi`, `g_esi`, `g_ebx`, `g_esp` through their TLV thunks) at every direct call the update makes (`runs/blx134/r9-edi/lldb.txt`): edi is 0x00FDD330 (the FE object) going into `sub_0019F370` and **0x0019F3B8** coming out, with esi = 0x350350 and ebx = 0x3503A0, and it stays wrong to the end. 0x0019F3B8 is a return address inside `sub_0019F370`. 0x350350 and 0x3503A0 are `ebx+0x150` and `ebx+0x1A0` (ebx = 0x350200, the camera object), two of the four arguments `sub_0019F370` pushes for its call to `sub_00237EA5`. esp itself comes back right, because `sub_0019F370` restores it from ebp, but it pops edi, esi and ebx 20 bytes too low: one return address plus four arguments were never popped.
- **`sub_00237EA5` lost its `ret 0x10`.** It is `D3DXMatrixLookAtLH` (D3DX section, 4 pointer arguments, stdcall), and it ends `leave; ret 0x10` at 0x237F95. The D3DX section header says VA 0x237D40, virtual size 0x260, **raw size 0x258**, so the file bytes stop at 0x237F98. The ret's encoding `C2 10 00` runs 0x237F96 to 0x237F98: its last byte, the zero high byte of the immediate, is not in the file. It is the XBE loader's zero fill between raw size and virtual size, and the linker relied on that. `tools/disasm`'s `BinaryImage.get_section_data` returns `raw_data[raw_addr : raw_addr + raw_size]`, capstone cannot decode the truncated `C2 10`, and the function ends at `leave` (functions.json: end 0x237F96). The translation ends `esp = ebp; POP32(esp, ebp);` and the C function returns with the return address and 16 bytes of arguments still on the guest stack.

**The prototype confirms it.** On toolkit branch `fix/spartan-boot-poll` (762fe10, off `posix-host/portability` b958798), `get_section_data` appends up to 14 zero bytes to an executable section whose virtual size exceeds its raw size, and the decoders do not start an instruction in that fill. Re-running `tca analyze` and `tca recomp` on a private copy of `spartan/tca` changes exactly one function bound (0x237EA5: end 0x237F96 → 0x237F99) and one generated file (`recomp_0067.c`: `esp += 20; return; /* ret 16 */`). The rebuilt title runs its front end loop: 4,800 presents in 90 s at about 14 draws a frame, no fatal-error screen, no `Couldn't find section` (`runs/blx134/r10-fixed/stdio.log`).

**BLiNX 2 and Burnout 3 do not hit it** because no real instruction in their code sections crosses the raw end. A/B disasm with the base and the patched toolkit (`runs/blx134/disasm-ab/`): Burnout 3, 24,000 functions, no bound changes. BLiNX 2, 18,670 functions, one change: `sub_00330162` in XGRPH, a phantom "function" made of string data, grows from 0x33131A to 0x33131D because the 3-byte `ss: add [eax], al` it ends in crosses XGRPH's raw end (0x33131C). Spartan's other raw-end cuts (XMV, DSOUND, XGRPH, D3D) end in data, and their bounds do not move.

**Nothing warned.** The lifter already knows when a body runs off its end with no fallthrough target (`translate_function`'s `continues_past_end`), but says nothing, because 55 bodies in Spartan's gen/, 1,358 in BLiNX 2's and 34 in Burnout 3's do that, nearly all data decoded as code. Filtered to bodies whose last statement is a frame teardown (`leave`, `pop ebp`), the count is 0, 0 and 0 on the fixed output (2026-10-15, `runs/blx134/scripts/falloff.py` with the epilogue filter), and the one body it would have named is the pre-fix `sub_00237EA5`. That filter is cheap and silent on the three titles, so it goes in as the regression guard for this class of bug (D3).

## What Changes

- **Toolkit `tools/disasm` (D1, the fix):** `BinaryImage.get_section_data` returns a code section's file bytes plus `min(virtual_size - raw_size, 14)` zero bytes, the loader's fill, so an instruction that starts in the file bytes can finish. `linear_sweep` and `decode_at` never start an instruction at or past the file end, so the fill is never decoded as code of its own. The gap-alias clamp in `functions.py` (`_build_alias_entries`) bounds an alias by the same data, not by `raw_size`, so it cannot cut the instruction the fix restores. Data sections, and code sections with `virtual_size <= raw_size`, are unchanged. Unit test `tools/disasm/test_section_zero_fill.py`. The prototype, e4e5315 + 762fe10, is D1 without the alias clamp.
- **Toolkit `tools/recomp` (D2, hardening):** the lifter's readers of function bytes (`Translator._read_func_bytes`) and its two raw-size extent checks (the coalesce request's "backed by one code section" test and its `analysis_end`) use one notion of a code section's readable end: the raw end plus the same 14-byte fill, read as zeros, not as whatever the file holds next. Today the file's padding is zero in all three XBEs, so D2 changes no output. It makes the lifter agree with D1 by construction.
- **Toolkit `tools/recomp` (D3, the guard):** `translate_function` prints one warning for a body that runs off its end with no fallthrough target when its last instruction is `leave` or `pop ebp`. Zero warnings on the three titles is a gate.
- **Spartan:** regenerate (`tca analyze`, `tca recomp`) against the fixed toolkit, then pin the toolkit release that carries it. `spartan/tca` is not a repo; the orchestrator applies it. The implementation branch is rebased onto the current `posix-host/portability` head (b53cb78, which carries the BLX-136 texture-format fix), so the post-fix Spartan run records whatever the front end shows next, not the magenta of 0x29.
- **BLiNX 2:** the goldens run on a scratch regeneration. `cat/src/recomp/gen/` itself follows its toolkit pin (`game.toml` `[toolkit]`, blinx2-v0.3.1) and is regenerated when the pin moves at the next push round, not in this change.
- **Tracker:** two missed XPP functions (0x27615C, 0x276B63, `[ICALL] Failed to resolve` during USB init, before and after the fix) get their own item: observed seeds for `spartan/tca/config/seed_functions.json`, and their effect on pad input is not yet known.

## Not in this change

- **The unfiltered run-off-the-end lint.** 55 / 1,358 / 34 bodies, nearly all data decoded as code (design "Alternatives"). D3 is the filtered form.
- **Zero-filling all of `virtual_size` for code sections.** The tail past the last instruction holds no code; handing it to the sweeps would create phantom functions in every title.
- **The XPP seeds.** Separate item, above. Texture format 0x29 (BLX-136) has landed already.

## Impact

- **Spartan:** boot passes the front end's first update; the title runs its front end.
- **BLiNX 2:** one phantom function in XGRPH gains one instruction it never executes; gen/ changes only in `sub_00330162` (`recomp_0098.c`). No runtime change is expected; the Metal and D3D11 goldens confirm it. cat's committed gen/ does not move until the pin does.
- **Burnout 3:** no function bound changes, so gen/ is expected to be byte-identical.
- **Hosts:** none. The change is in the generation tools; the runtime is untouched.
- **Upstream:** D1 to D3 are title-neutral and touch files upstream has unchanged (`loader.py`'s `get_section_data`, `config.py`'s `va_to_file_offset`, `_read_func_bytes`); they join PR 1 (recompiler and disasm) of `cat/analysis/upstream/pr-stack-plan.md`.
