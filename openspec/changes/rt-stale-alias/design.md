## Context

- Metal (`nv2a_pb_metal.m`): `surface()` makes or reuses a target keyed by (offset, w, h), LRU over `RT_MAX` 8 slots, seeds a new 32-bit target from the guest bytes, and never looks at overlaps or at whether a reused target's memory changed. `rt_texture()` matches a stage by exact address (low 27 bits) and nothing else. `tex_bind()` writes back (`rt_sync`) every dirty target that overlaps the bytes it is about to hash and decode, whatever its size, so a 64 KB texture inside a 1 MB target costs a 1 MB write-back. `rt_free()` writes back a dirty target only if it was presented. Write-back is lazy by default (`metal_writeback=lazy`), so the guest bytes under a drawn target stay what they were before the draw until something asks for them. `dirty` says "drawn since the last write-back"; there is no per-flip draw mark (`last_use` is a `surface()` tick, not a flip).
- D3D11 (`nv2a_pb_d3d11.c`): the same `surface()` and `rt_texture` matching, with `last_draw` and `last_clear` sequence numbers. It never writes guest memory, so the stale binding is the only fault there.
- CPU: draws into guest memory and decodes from it, rehashing per draw. Nothing to fix.
- `metal_fb_guard` (debug): the present surface's pages are PROT_NONE after each flip and a signal handler records the first title access. Its own note says it is debug only: a kernel-side `read()` into those pages fails with EFAULT, which is exactly how a stage load lands in guest memory.
- Evidence: user log 101123 (hub targets created at line 9318 and never retired, the stage's water targets inside the hub's 0x0119B000 MB, "2 decode syncs"), `water-metal.mov` against `water-reference-youtube.mov` (plates red against cyan), and the user's report that a render-scale change cleared the textures.

## Decisions

1. **Ownership by content, not by time or by traps.** A target that has not been drawn for a while can still be a legitimate texture (rendered once, sampled for many frames), so ageing is wrong. The runtime has no write tracking on guest memory: recompiled stores go straight to the mapping, so a generation counter has nothing to increment, and page traps (`mprotect`, the `fb_guard` machinery) break kernel-side I/O into the pages and cost a fault per first touch. So each target keeps `mem_hash`, `nv2a_tex_hash` over its guest bytes (pitch x h, clamped to the memory window, through the low 27 bits of the address), taken when the backend last knew them: at creation, from the same bytes the seed reads (and for a 16-bit surface, which is not seeded, from the bytes all the same), and after each `rt_sync`, from the bytes just written. If the guest bytes no longer hash to `mem_hash`, only the title can have written them: it has reused the memory, and the target is stale.
2. **When to check.** Only for a target not drawn in the current flip (`draw_flip != flips`; `draw_flip` is set where `dirty` is set, in `begin_pass`, and by clears), when it is about to be (a) bound by `rt_texture`, (b) written back by the decode sync, by eviction or by `sync_guest`, (c) retired by an overlapping creation, or (d) reused by `surface()` for a new draw. Once checked in a flip it is not rehashed again in that flip (`checked_flip`). A target drawn this flip is the title's surface by definition. The present target is drawn every flip, so under `metal_fb_guard` its pages are never hashed while armed; a check that does reach guarded pages calls `guard_open()` first, as the seed read does, since it is not a title read.
3. **Stale means drop, never write back.** A stale target is freed with `dirty = 0`, so neither `rt_free` nor the decode sync copies it. Its pixels are lost, which is correct, since the title replaced them. A stale target found by `surface()` on reuse (case d) is dropped and recreated, seeded from the title's new bytes, as hardware would draw over them; today the old GPU image is drawn over instead.
4. **Overlap retirement.** When `surface()` creates a target, any other target whose guest range (pitch x h, low 27 bits) overlaps the new one in whole or in part is retired by the same rule: written back if its memory is unchanged, dropped if it changed. The write-back comes before the new target's seed read, so the seed sees what was drawn. Two live targets never alias. `rt_texture` keeps its exact-base match; a texture inside a live target but not at its base goes through the decode sync, as today.
5. **Shared helper.** `struct nv2a_rt_own { uint64_t mem_hash; uint32_t draw_flip, checked_flip; }` embedded in both backends' `RenderTarget`, with `nv2a_rt_own_reset(own, mem, addr, pitch, h)` (hash now), `nv2a_rt_own_drawn(own, flip)` and `nv2a_rt_own_stale(own, mem, addr, pitch, h, flip)` (rehash when not drawn this flip and not yet checked this flip) in `nv2a_backend_common.h` and `.c`. The ctest drives the helper directly, with a buffer in place of guest memory.
6. **Cost and its bound.** `nv2a_tex_hash` is four FNV lanes over 8-byte words: a few tenths of a millisecond per MB on an M-series core. At most the targets not drawn this flip are hashed, each once per flip, so the worst case is seven 1 MB targets, which is why `checked_flip` matters and why `metal_prof` gets a row for it. If the measured cost is too high on stage1 3x, the fallback is a row-sampled hash (every eighth row plus the first and last): a loader rewriting the block touches every row, and task 1.3's inventory of what stage 1 keeps there bounds the smallest rewrite that must be caught. Decide on the measurement, not in advance.
7. **Escape hatch and visibility.** `RECOMP_DEBUG=rt_alias_check=0` restores today's behaviour for A/B runs, on both backends, with a row in `docs/env.md`. Each drop logs one line (first 20) naming the target, its size, the reason (bind, sync, overlap, reuse) and the flip; the present summary line gets a "stale drops" count, and `RECOMP_TRACE=metal` names the target and the texture for every decode sync, so the "2 decode syncs" of the repro become attributable before the fix.

## Repro and proof

- `@hub-stage1`: `@story-hub` (empty save to the hub, where the 512x512 targets are created), then into stage 1-1. The hub-to-stage route is a task: either the hub's own stage door, or the debug stage select reached from the hub's title return. Its first step finds which one works headless.
- Proof of corruption, on the integration build before the fix: `mem_dump` of 0x0169D000 and 0x0119B000 (1 MB each) at the first stage-1 frame and again after the first decode-sync line, compared with `cmp -l`, and against the CPU path's dump of the same block at the same flip, which is the truth. The second Metal dump should hold the hub image (BGRA rows at pitch 2048) where the first and the CPU dump hold stage data. After the fix the Metal dumps should match the CPU dump, with no decode sync on the stale target.
- Frames: `fb_dump` on the plates (or barrels) on Metal 1x and 3x, before and after, against the CPU path on the same route.

## Risks

- **A title that rewrites a target's memory and then expects the old rendered image back.** Impossible on hardware, because the rendered image lives in that memory, so the rule matches the hardware.
- **A target cleared or written by the CPU before each draw** (a memset, a dynamic texture composited by the GPU). The memory changes, so the old target is dropped and recreated from the new bytes on the next draw: one creation per draw, which is correct and was wrong before. A target recreated every flip shows in the drop log and the summary count.
- **Overlap retirement writes back an unchanged dirty target** that nothing wrote back before (new Metal behaviour, up to 1 MB). It happens once per overlapping creation and is what hardware memory would hold.
- **A rewrite that hashes equal** (the same bytes written again) keeps the target: harmless.
- **Goldens.** `@story-hub` creates and samples the hub targets every flip, so its frames should be unchanged; `@stage1` does not pass through the hub, so the alias is not in it. Any verdict change is investigated, not re-recorded. `metal_writeback=always` and `metal_fb_guard` are unchanged in what they write and trap; the only new reads of guest memory are the hashes.
