## Context

- Each guest thread runs on a host thread. Guest code at DISPATCH_LEVEL and above, ISRs and DPCs are serialised by the one-CPU gate (`kernel_hal.c`, `irql_track_gated`, `xbox_IrqPost`). Passive guest code runs in parallel on every core the host gives it, and that is where BLiNX 2's light-pool race lives (BLX-1; `runs/water/`, `bench-logs/20261007-134259`).
- The pin (`xbox_GuestThreadPin`, `kernel_thread.c`) puts the title's threads on one core on Win32 and Linux. macOS has no `pthread_setaffinity_np`; the pin prints one line and does nothing. On the hosts where it works, a host tick inside the few-instruction window still loses an entry.
- Upstream v0.13.1's `RECOMP_GUEST_LOCK` (`kernel_bridge.c`, `guest_cpu_enabled`/`guest_cpu_join`/`guest_cpu_part`/`kernel_thunk_dispatch`): a recursive `CRITICAL_SECTION` a guest thread holds while it runs guest code and lets go for the length of every kernel call. Host threads that run guest callbacks (the timer thread's DPCs, the device models' ISRs) never take it. Default off. Upstream's own comment: a guest thread spinning on a flag another guest thread sets, with no kernel call in the loop, deadlocks; the upgrade it names is a periodic yield point in the lifted code's backward branches.
- On BLiNX 2 (Mac, Metal, attract) it paced at 23.1 fps vs 58.3 (upstream-sync design row 16). The title's threads: guest-main and five `PsCreateSystemThreadEx` workers at routine `0x002980E7` (the XDK's thread-pool entry; DirectSound streaming and the stage loader run through it).
- The lowered spin-wait: `tools.recomp --spin-waits` turns a listed guest busy-loop's back edge into `RECOMP_SPIN_WAIT(va)`, which calls `xbox_SpinWait` when the pacing mode is sleep or an interrupt is posted (`g_xbox_spin_sleep | g_xbox_irq_pending`). `xbox_SpinWait` is the gate holder's safe point and, in sleep mode, a 1 ms bounded wait. One site is lowered in cat: the main loop's frame wait at `0x00060475`. `analysis/recomp/spin_waits.json` lists 12 more candidates, among them `0x00334325`, the DSOUND submit's wait for the GP doorbell that the toolkit's APU frame thread clears on each pass (`apu_dsp_ack=auto`).

## Decisions

### D1. Build on upstream's lock, not beside it

Alternative A of `guest-one-cpu` described a guest-CPU token released at every kernel wait, at the spin-wait yields and on a quantum. Upstream has since landed the first two thirds of it under `RECOMP_GUEST_LOCK`. The operator's rule is to build on upstream's mechanism where one exists for the same problem; the audit it needed (every blocking path drops the token) is done by construction in upstream's design, since every bridge call drops it, not only the waits. The switch, the entry names and the release rule stay upstream's; the body moves into `kernel_guest_cpu.c` behind `xbox_GuestCpu*` so `kernel_bridge.c` keeps upstream's few lines and the next sync merges cleanly.

### D2. The console's scheduler, not a critical section and not a fair lock

A thread that releases a `CRITICAL_SECTION` and takes it again a few instructions later usually gets it back before a waiter wakes (neither NT's nor pthread's mutex is fair). Under upstream's lock a worker that took the CPU when the main thread blocked then kept it through its whole burst, every one of its own kernel calls retaking the section before the main thread woke: Mac attract 28.5 flips/s against 32.4 with the lock off, p95 70 ms (tasks 1.1, `runs/maccpu/pacing/sync-lock{0,1}.log`). The first fix tried was the opposite, a ticket lock that handed the CPU to the oldest waiter at every release: 12.7 flips/s, p95 325 ms (`new-lock1-ticket.log`). The title makes a few hundred kernel calls a frame (IRQL raises and lowers, event sets), and each hand-off is two context switches and a condition-variable wake; the frame went to scheduling.

The console's scheduler did neither: a kernel call that returned at once switched nobody, a blocking call ran the next ready thread, a quantum expiry did too, and a yield gave the CPU away. The guest CPU does the same, over one critical section and one condition variable:
- a kernel call is a soft release: the CPU is marked free and the caller takes it straight back on return if nobody took it meanwhile, barging past the queue;
- a call that may block (the waits, `KeDelayExecutionThread`, file I/O, `NtSuspendThread`: a short ordinal list) wakes the waiters, so one takes the CPU if the caller blocks; a waiter also looks on its own every 2 ms, so a bridge that blocks without being on the list costs latency, not a hang;
- a thread that has held the CPU for its quantum (`guest_quantum`, default 4 ms) with another waiting hands over at its next kernel call, whatever the call: the oldest waiter is granted the CPU, barging is refused until it has taken it, and the releaser queues behind every waiter;
- a thread with nothing to do hands over at once: a lowered spin-wait's pass (D3), `NtYieldExecution`, the thread's end.

Uncontended cost: one lock/unlock pair per release and per acquire, no wake.

### D3. The spin-wait pass yields at every pacing

`xbox_SpinWait` is the one place lifted code already calls the host from inside a loop, between two guest instructions, with its registers in the TLS and nothing half-done: the gate holder's safe point lives there already. A pass with another guest thread waiting for the CPU releases it, which hands it over (D2), and takes it back, which queues behind the waiters; the loop's next pass re-reads its condition. In spin mode that is the whole yield; in sleep mode the 1 ms wait happens without the CPU. The macro's condition gains `g_xbox_guest_cpu_waiters`, a volatile int the lock keeps as the count of threads waiting (one relaxed load per pass; the macro already reads two). The order inside `xbox_SpinWait` stays: safe point (a posted ISR runs holding the CPU, as an interrupt runs on the console with no thread in between), then the yield. A pass at DISPATCH (or with the gate held) does not yield, in either pacing mode: at DISPATCH the console's scheduler switched no threads, and the DPC such a loop waits for is held off by this thread's own IRQL, not by the CPU; the site counts the pass under `dispatch`.

This ends the deadlock upstream describes for every lowered loop, and it is a lifter-config change, not a lifter change: a guest loop that spins on another guest thread's work, or on a host thread's (the APU doorbell, the GPU's fence word), is listed in `spin_waits.json` and lowered at the next recomp. The hold diagnostics (D6) name the loops that need listing; the title's own `analysis/recomp/spin_waits.json` candidate list is where they are found. A loop the matcher rejects (one that writes memory in its body) is a lifter follow-up, not this change's.

At DISPATCH nothing hands over: the back edge, the spin-wait pass and the kernel-call release all refuse while the thread holds the DISPATCH gate (the thunk releases at every ordinal, `KfLowerIrql` and `KeReleaseSpinLock` included, with the gate still held; a hand-off there would queue the gate holder behind waiters whose next `KfRaiseIrql` blocks on the gate). The soft release at such a call still frees the CPU for the length of the call, and a waiter at its 2 ms poll may take it: a gap that predates this change and is recorded as a follow-up (TASKS).

### D4. Who holds the CPU

Held: guest-main from `xbox_kernel_bridge_init` (upstream's join) to exit; every `PsCreateSystemThreadEx` worker (`bridge_thread_main`) and a worker run inline on its creator's thread (`bridge_run_thread_inline`); and guest code a bridge runs on a guest thread, which is thread code on the console too: the APC completion routine (`NtUserIoApcDispatcher`), unwind handlers (`RtlUnwind`), the `KeSynchronizeExecution` routine. `kernel_thunk_dispatch` takes the CPU back when it had it on entry (not upstream's depth-0 rule), so an inline worker's kernel calls restore it and a callback's nested calls leave it as they found it.

The title's main thread is one of these callbacks and was missed at first: `bridge_PsCreateSystemThreadEx` (and `bridge_PsCreateSystemThread`) run the first thread created, the title's main thread, by calling its routine inside the kernel call, where the dispatcher had soft-released the CPU. Without the callback entry the main thread ran unlocked for the whole title against every worker, which is the race the lock is for, and the first cut's "pacing equal to lock off" was measured that way. The per-thread table of D6 showed it: tid 1001 never appeared, and the lowered main-loop site 0x00060475 counted millions of passes with a waiter and no hand-over. Both sites wrap the routine in `xbox_GuestCpuEnterCallback`/`LeaveCallback`; `tests/kernel_bridge` checks the routine holds the CPU and the caller has it back after the call.

A replaced XDK routine in cat that waits on the host without a kernel call holds the CPU through its wait, which no ordinal releases. `sub_002E0DB0` (`D3DDevice_BlockUntilVerticalBlank`, the 60 Hz pacer the ADX threads call) slept in `xbox_HostSleepNs` holding it: the two ADX threads held the CPU 7.7 s of every 10 s with no CPU time, every other thread's waits averaged 17 ms, and the movie decoder's frames came late. `XBOX_GUEST_CPU_HOST` is the release kind for such a wait: a hand-off when a waiter exists, otherwise a soft release that wakes the pollers; the routine takes the CPU back after the sleep when it had it. Any future hand-written routine that sleeps or blocks on the host must do the same.

Not held, as upstream decided: ISRs and DPCs, on the device models' threads, the timer thread, or a guest thread running one at a safe point or at its raise (BLX-2). On the console an interrupt ran between any two instructions of any thread; a title protects what an ISR or DPC touches by raising IRQL, and the one-CPU gate gives that. Taking the guest CPU for a DPC would also bring back the deadlock: a guest thread spinning in an unlowered loop on the DPC's result, holding the CPU the DPC waits for. What stays different from the console is that passive guest code can now observe a DPC's intermediate state from another core (a DPC's body was atomic against passive code on the console; passive code never was against the DPC). Unchanged by this change on every host, recorded here.

### D5. The quantum at loop back edges

A guest thread computing for long without a kernel call or a lowered loop holds the others off for that long; the console's timer tick would have switched at the quantum wherever the thread was. The kernel-call quantum check (D2) does not reach it: under Proton the story menu's main thread runs a whole frame of lifted code with no kernel call, lets go only at the main loop's spin site, and the movie worker waits 10-25 ms per turn (the title movie at 52 changes against 72 with the lock off; story-menu FAIL 3 of 3 at mae 2.8-5.0, 22.6% bad). The first cut of this change left the back edge for the evidence (the Mac passed by a smaller margin); this is it.

The preemption point is `RECOMP_BACK_EDGE(va)` at every loop back edge of lifted code: `tools.recomp` wraps each jump whose target is at or before its block's start (a block has one entry, so that is every backward jump) as `{ RECOMP_BACK_EDGE(0xJUMPu); goto loc_T; }`, except the edge a spin-wait lowering already owns. The macro is `if (g_xbox_guest_cpu_preempt) xbox_GuestCpuPreempt(va)`: a waiter in `guest_cpu_acquire` that has waited its quantum sets the flag at its 2 ms poll, the holder sees it at its next back edge and hands over there (`XBOX_GUEST_CPU_PREEMPT`, "back edge 0xVA" in the summary), queuing behind the waiters as at a spin-wait yield; the hand-off clears the flag. The edge is between two guest instructions with the registers in the TLS and nothing half-done, the same place a lowered loop already calls the host from, so the hand-off is as safe as D3's. Not at DISPATCH (D3), and a non-holder (a host thread's callback, the lock off) returns at once without touching the flag.

Why this point and not another. A frequent toolkit entry (the pushbuffer or MMIO path, the KickOff) is not on every long stretch: the NV2A registers are plain memory here and the kick is polled by a host thread, and a decoder or a loader loop touches neither. A signal or `SuspendThread` from a watchdog preempts anywhere, including inside a host library call with a host lock held, which the waiter's guest code may then need: a deadlock the console never had. The back edge is the one point every long computation passes, and the only one that bounds a turn to the quantum unconditionally; upstream's README names it as the lock's upgrade.

Cost on the hot path: one relaxed load of a global int and a branch not taken per backward jump, in every lifted function, the lock on or off (the flag never rises with it off); the flag is written only by a waiter past its quantum and by the hand-off, so the line is read-shared. Measured on the Mac (Metal, attract, `pacing-stats` anchored at title-3d, 97,251 sites in cat's gen; task 10.4): 32.89 flips/s, p95 33.43 ms, process CPU 117% before the regen against 32.92, 33.44 and 117% after, so the check costs nothing the pacing can see; with the lock on it takes about 5% of the turns (540-582 preempts of 11,300 in attract, 65-77 of 5,800 in the story run). The lifter switch `--no-back-edge-yield` leaves the edges bare for a title that wants the old output; cat regenerates with the default (`blinx2 analyze` then `blinx2 recomp`).

**The wake boost.** The back edge alone bounded every wait to the quantum plus the poll (Proton, toolkit e48f150: longest wait 6-7 ms against a frame before) but left the menu's title movie at 59 changes against 72 and story-menu failing 3 of 3 (bad 8.6-20%): the movie's worker threads (the per-thread lines of `runs/blx31-proton/logs`'s cadence run, tids 404 and 408) each waited 1.4-1.7 ms on average for the CPU at every wake, 3.2-3.7 s of a 10 s window for 0.1-0.4 s of CPU, and a movie frame is a chain of such wakes. On the console a thread leaving a wait is boosted above the thread it interrupts (KeSetEvent's increment, the I/O completion's) and runs at once; cat never sets a thread priority (no KeSetBasePriorityThread or KeSetPriorityThread call in its code), so the boost is the whole priority story. The scheduler does the same: a thread back from a kernel call, a host wait or into a callback (`guest_cpu_acquire(barge=1)`) that finds the CPU held raises the preempt flag at once and the holder hands over at its next back edge or kernel call; a thread that yielded or was preempted (`barge=0`) raises it only past the quantum, the round robin of equal priorities. A bridge that blocks on the host inside an ordinal that usually does not (`RtlEnterCriticalSection` contended: the holder of the section is a guest thread that needs the CPU to leave it) calls `xbox_GuestCpuBlocked` so the pollers learn at once that the CPU let go of at the call stays free, instead of at their 2 ms poll. Nothing changes on the back edge itself; the cost is more hand-offs, each a condition-variable wake: on the Mac's attract the preemptions went from 540-580 to 2570-2710 a 600-flip window for 32.92 against 33.03 flips/s and 117% against 118% process CPU; under Proton the menu's title movie came back to 72 changes (the lock-off figure) and story-menu to CLOSE 3 of 3 at mae 0.78 (tasks 10.6, 10.7).

### D6. Diagnostics

`[PACING]   guest cpu: turns N (yields N), kernel calls N of which switched N, waits N; longest turn X ms (ordinal N | spin 0xVA | host wait 0xVA | callback end | thread end), longest wait Y ms`, every 600 flips with the rest of the pacing summary, counting from the last one, followed by one line per guest thread (up to 16 slots, claimed by tid and never freed): its kernel calls, turns and own hand-offs, wall time held and CPU time used in those turns (the two differ when the thread sat in a host wait with the CPU nominally its, or was not scheduled), the longest turn with its CPU time and end site, yields, its waits with the longest, the longest kernel call taken straight back (nobody took the CPU while it ran) and the longest run of guest code between two lets-go with the ordinal that ended it. The CPU column is what tells a thread that computes from one that holds while blocked, which is how the two faults of D4 were found; the two "longest" columns tell a call that blocked with no taker from guest code off the CPU. Each lowered spin site's line gains `spin passes with a waiter N, handed over N`: a site with many passes and no hand-overs is a holder the lock never reaches. The per-thread table and the thread CPU clock (GetThreadTimes under Wine, a wineserver round trip, at thousands of turns a second) are kept only when the pacing or the `guest_cpu` trace is on; the window counters always are.

`RECOMP_TRACE=guest_cpu[=ms]` logs each turn longer than ms (default 1) as `[GUEST] cpu held X ms by tid T, released at ...`, the first 50 then one a second. A turn ends at a kernel call that hands over (the ordinal), a spin-wait yield (the VA), a host wait (the VA), a callback's end or the thread's end (`PsTerminateSystemThread` hands over before `ExitThread`, so the last turn closes); the record is kept per thread in TLS at the release and reported at that release, so nothing reads another thread's registers.

### D7. Lock order against the one-CPU gate, and the BLX-2 drain

A thread takes the gate inside a bridge (`KfRaiseIrql`, `KeSynchronizeExecution`, a DPC's `xbox_IrqlEnterInterrupt`), where the guest CPU is released, and takes the CPU back on the way out while still holding the gate: the order is gate, then CPU. Nothing takes the gate while holding the CPU: the safe point inside `xbox_SpinWait` runs a posted ISR through `xbox_IrqlEnterInterrupt(16)`, which does not go through the gate, and `irq_release_point` uses `gate_try`. `KeSynchronizeExecution` takes the gate first (upstream's order), then the CPU for the routine. So there is no cycle.

The BLX-2 DPC drain (`fix/dpc-on-irql-raise`, `dpc_run_here`) runs DPCs on a guest thread inside the raise bridge and at the release point inside the lower bridge: both inside a kernel call, CPU released. A DPC routine is guest code, though, and on the console it runs at DISPATCH level with nothing else running; here it runs while another guest thread may hold the CPU, exactly as it does on the timer thread (D4: a DPC never takes the CPU). The first cut of the rebase wrapped `xbox_DpcDrainHere` in the callback entry; the Fable review showed the cycle that opens: the drain runs under the gate (`gate_enter` in the raise bridge, `gate_try` at the release point), so a thread blocked in `guest_cpu_acquire` there holds the gate while a holder spins in an unlowered loop on that very DPC's result, and the timer thread's drain, which would run it, waits for the gate. The wrap is gone; the one-CPU gate is what a DPC's body is atomic against, and `tests/dpc_order` (g) asserts the routine ran without the guest CPU. `xbox_DpcMarkGuestThread` is called from the thread-role log on that branch for the same threads this change's join marks, so the join needs no call; the branch merges onto `integrate/sync-dpc` (5b849c7) without conflict.

### D8. Defaults and the pin

The toolkit's default stays off (upstream's), and nothing moves for Burnout 3 or any other title. cat turns it on in `src/main.c` when the environment does not say otherwise, as it does `RECOMP_VBLANK` and `RECOMP_TITLE_KEVENTS`; `RECOMP_GUEST_LOCK=0` is the A/B. The pin keeps its default (one core on Win32 and Linux) in this change: with the lock on it is redundant, but whether the hand-off paces better on one core (the waiter wakes on the core the releaser is leaving, as on the console) or on several (the waiter is already on another core) is a Proton measurement, not an argument. Tasks 6.x ask for `RECOMP_GUEST_CPUS=all` against the pin, both with the lock on, on stage 1 and the hub; if `all` is no worse, the pin's default moves to `all` when the lock is on, and `guest-one-cpu`'s requirement is rewritten then. Measured under Proton (tasks 7.2, toolkit 32cd6fd): with the lock on, `all` equals the pin on stage 1 and the hub (29.98 and 30.00 flips/s both ways, p95 within 0.1 ms, same golden verdicts, hub race 0 of 10 bad with the pin off). The gate agent's recommendation is `all` as the default when the lock is on (the pin stays for the lock-off arm). Recorded as a recommendation: the default does not move in this change; that is the user's call.

## Alternatives

- **The pin plus a Mac-only mechanism** (a Mach thread policy, `thread_policy_set` with `THREAD_AFFINITY_POLICY`, is a hint on Apple silicon and ignored for scheduling): no guarantee, and two mechanisms for one problem.
- **A lock in the title** around `sub_00037CE0`: rejected in `guest-one-cpu` (alternative B); the pool is reset by plain stores in a dozen functions and other titles have other globals.
- **The lifter's back-edge yield now**: D5.
- **ISRs and DPCs take the CPU too**: D4.

## Risks

- A guest loop not yet listed that spins on another guest thread's work holds the CPU until that thread runs: a hang where today there is none. The `[IRQ] wait` log and the `guest_cpu` trace both name the holder; the mitigation is `RECOMP_GUEST_LOCK=0`. The attract, stage 1 and story routes and the goldens cover what BLiNX 2 does on its known paths; the operator's play-through covers the rest, with the Steam Deck build on the pin and the lock.
- Pacing: upstream's lock loses 12% of flips headless (p95 doubles); a fair ticket lock loses 60%. Section 5 of the tasks records each arm; the scheduler of D2 paces inside the lock-off spread on the attract and stage 1 routes.
- Load timing: one CPU serialises the loader with the main thread, so a load ends later by the main thread's share (the attract title's fade-in starts 6 flips later on the Mac than with the lock off; stage 1's first 3D flip comes 10 flips earlier). Goldens anchored on a fade or a movie phase move with it; the pin under Proton serialises the same way, and the references were recorded there.
- Movie cadence: the Sofdec decoder is a guest worker, and with the first cut its frames came late on the Mac (the opening movie at ~23 fps instead of 30, the title movie behind the story slot list at 15). Not a quantum problem (tasks 4.3) but the two faults of D4: the ADX threads holding the CPU through the vblank pacer's host sleep, and the main thread running outside the lock. With both fixed the movies run at full rate (tasks 4.4). A hand-written routine that blocks on the host without the `XBOX_GUEST_CPU_HOST` release brings the first one back; the accounting of D6 shows it as a thread with wall time held and no CPU.
- The host's own stalls: on the Mac used for the gates (35 of 36 GB in use, 6.5 GB in the compressor, 4 GB of swap), every 5.0 s the main thread accrues no CPU for 60-340 ms while runnable (`ps -M` state R, and the sampler's own 100 ms tick stretches to 150 ms at the same moments), so the per-thread line shows a turn of 100-340 ms with 20-90 ms of CPU ending at the main loop's spin site, the ADX threads waiting as long, and the flip log a stall of the same length; a 30 s stack sample shows the main thread in guest code, never in a syscall. A lock-off run stalls the same way (tasks 4.5). With the lock on, a stalled holder stalls the waiters too, which is the console's behaviour on a stalled CPU. Not the lock's to fix; the cadence figures of 4.4 were taken through it.
- Proton: Wine's `CRITICAL_SECTION` and `CONDITION_VARIABLE` are the lock's primitives there; a hand-off is a futex wake and a schedule. Owed to the bench agent with the goldens (tasks 6.x).
- The wake boost's flag is global: a boosted waiter raises it at every poll whatever its place in the queue, so a boosted thread that has just been handed the CPU can be preempted at its first back edge by the boosted thread queued behind it (each hand-off still makes progress, and the hub race and the goldens are clean). Follow-up: raise only when no boosted waiter is ahead (`my == s_head`).
- Signal-handler context on POSIX: the lock is never touched inside the MMIO fault handler (the executor runs on the nv2a-ack thread; the APU and OHCI traps touch no guest-CPU state), so `pthread_mutex` async-signal rules do not come up.
