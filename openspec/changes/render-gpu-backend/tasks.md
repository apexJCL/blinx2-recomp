## 4. Metal GPU render backend (macOS; spike Phases 3-4; M1 skeleton and M2 programs done)

**Goal:** BLiNX 2's 3D drawn by the Mac GPU through Metal, replacing the CPU rasteriser as the macOS render path, while the SDL2 window stays the Present path. Done means the attract and `@stage1` frames match the Proton D3D11 golden frames within the golden tolerance, at the game's 30 Hz pacing (about 30 flips/s, p50 at or under 33 ms), with the CPU render path still selectable as the oracle. Today the macOS GPU only blits the CPU-rendered frame; this section is what turns it into a render backend.

**Gate:** starts only after Proton is playable (user decision 2026-10-02). Builds on the shared NV2A state layer (P0/P1, toolkit d050739) and the SDL2 window on the main thread (P2, toolkit 35e8831), which are merged.

- [x] 4.1 Backend skeleton: `RECOMP_PB_BACKEND=metal` registers an executor backend on macOS that consumes the shared layer's decoded state (same ABI as `nv2a_pb_d3d11.c`). Clears and screen-space batches into an `MTLTexture`; the fence write stays in the executor, in stream order. (M1: toolkit `src/d3d/nv2a_pb_metal.m`, Obj-C, MRC; MSL compiled at runtime with fast math off.)
  - [x] 4.1.1 `tests/nv2a_backend_smoke` (POSIX, backend-neutral; replaces `d3d11_backend_smoke` on macOS): clear + quad, swizzled checker, YUY2 and an alpha-blended quad, each drawn by the CPU rasteriser and by Metal in one process, plus a quad with fractional edges to catch a half-pixel offset. Each scene must match exactly, and all four do, and the test is registered with ctest.
  - [x] 4.1.2 Interim Present (until 4.5): at FLIP_STALL, read the presented `MTLTexture` back into the guest present surface and call `xbox_FramebufferWindowPresent`, so the window, `RECOMP_FB_DUMP` and `RECOMP_WINDOW_SHOT` read it as on the CPU path. `RECOMP_FB_DUMP_FLIPS` now counts the batches of a backend that writes back (`writes_back`, Metal only) as drawing.
