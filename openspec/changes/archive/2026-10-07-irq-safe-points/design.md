## Context

- The one-CPU gate (`s_dispatch_gate`, `kernel_hal.c`) is a recursive host critical section. A thread raising to DISPATCH takes it (`irql_track_gated`, with `t_dispatch_gate_held`), the timer thread's DPC drain takes it with TryEnter (`kernel_drain_dpcs`) and `kernel_run_dpc` through `xbox_IrqlEnterInterrupt(2)`, and KeSynchronizeExecution takes it with a blocking Enter. It is how the runtime stands in for "one CPU at DISPATCH". Nothing records which thread holds it beyond the critical section itself.
- Device interrupts are delivered from host threads: APU (`apu_deliver_irq`, frame thread, with `d->lock` dropped around the routine), OHCI (`ohci.c` controller thread) and vblank (timer thread, `kernel_raise_interrupt`). Each tries the gate. When it is busy: the APU holds off up to 50 frames and then forces, OHCI holds off up to 500 polls, and the vblank never waits. The APU frame thread must not block on the gate: a DSOUND DPC holding the gate waits on the frame thread to clear a trapped FE method (`fe_trapped`), and Burnout 3's vehicle select once froze on that pair.
- The vblank tick sets PCRTC_INTR_0 and PMC_INTR_0 and `g_vbl_tick_busy` before the ISR, arms the ack watch on a claimed or declined ISR, and counts declines; `xbox_VblankAckWait` runs on the nv2a-ack thread.
- MMIO traps: APU and NV2A register accesses fault and are emulated inside the fault handler (`apu_mmio_hook.c`, the NV2A hook), which already avoids creating threads there because of the loader lock.
- Evidence for the hang: `sample-hang2.txt` code offsets match this tree's build (`sub_003346BE`+848, +968 and +1204 in the second loop). The thread dump shows thread 16 waiting for the gate in KfRaiseIrql, holding nothing. The disassembly (`analysis/disasm/asm/DSOUND.asm`) shows the list drain, the unguarded tail insert, and the interrupt path that reaches it.
- Not yet confirmed: that a forced or ungated delivery happened in the user's session. A 140 s stage-1 run showed `forced 0` (`runs/stage1-issues/m1-apuirq`). The user's `RECOMP_TRACE=apu` repro (forced count before the hang) is task 1.1.

## Decisions

1. **Deliver on the holder, at safe points.** On hardware an interrupt runs on the interrupted CPU between two instructions. The holder of the gate is our "CPU at DISPATCH", so running the routine on the holder's thread, between two guest operations, is the faithful model. Concurrent delivery is not. Blocking the deliverer instead is not an option: the APU frame thread and the timer thread are what the holder may be waiting for.
2. **Safe points are where guest code already calls into the host, outside any guest read-modify-write.** Kernel thunk entry (`kernel_thunk_dispatch`, before the bridge runs and before any host lock), the spin-wait yield (`xbox_SpinWait`, before its `xbox_IrqlThisThreadBlocksDpcs` early return, which is the holder spinning at DISPATCH) and the gate release, taken while the gate is still held: `irql_track_gated` on the lower that would leave, the end of `kernel_drain_dpcs`'s routine before `xbox_DispatchGateLeave`, and the end of `bridge_KeSynchronizeExecution`. A serviced MMIO trap is not one (proposal); a guest poll loop on a register that needs the interrupt is a `spin_waits.json` site, and the `irq_safe_ms` log names the loop to add.
3. **Gate ownership is explicit.** A thread-local gate depth counts every entry through `irql_track_gated`, `xbox_IrqlEnterInterrupt(2)`, `kernel_drain_dpcs`, `KeSynchronizeExecution` and the deliverers' own TryEnter. A safe point delivers only when this thread's depth is non-zero: a non-holder at a thunk never runs a pending routine, since that is the concurrent delivery this change removes. A thread running a posted routine has a thread-local `in_isr` flag, so a safe point inside the routine (its own kernel calls) does not nest; what is posted meanwhile runs when the routine returns, in the same safe point's loop. The same flag covers the deliverers' direct runs, so an ISR delivered by the APU thread with the gate never takes a nested one either.
4. **Pending word and the post protocol.** One atomic word with a bit per vector (vblank, APU, OHCI); a set bit coalesces repeats, as a latched line does. The deliverer: TryEnter; if it has the gate, deliver as today; else set the bit, then TryEnter again. The second try closes the window in which the holder released between the first try and the post, with no safe point left to see the bit: if it succeeds, the deliverer clears the bit and delivers itself. The holder's safe point: one relaxed load when nothing is pending; else exchange the word to zero and run each set vector's routine, looked up from the connected interrupt at delivery time (`xbox_GetConnectedInterrupt`), so a routine reconnected in between is the one that runs. A level-triggered line that dropped before delivery still gets its routine: the ISR reads its status register and declines, as on hardware.
5. **Register and stack discipline.** The routine runs on a worker stack (`xbox_worker_stack_alloc`, 16 slots). If none is free the bit stays set, the safe point returns, and one log line says so. The holder's recompiled register state (every `RECOMP_TLS` register the generated code keeps live across a call: `g_eax`..`g_edi`, `g_esp`, `g_seh_ebp` and whatever else the thread-dump code saves; the implementer lists them from the generated header) is saved and restored around the routine, since a thunk entry safe point sits before the bridge reads its `__fastcall` arguments. `g_fs_base` is the holder's own. The IRQL goes to the device level with `xbox_IrqlEnterInterrupt(16)` and back with `xbox_IrqlLeaveInterrupt`, whose `xbox_SpinWake` stays, so a sleeping spin wait re-reads what the routine wrote. A KeSynchronizeExecution holder sits at PASSIVE with the gate: the raise to 16 counts and uncounts as any ISR's does today.
6. **No concurrent fallback by default.** A holder that reaches no safe point within `irq_safe_ms` (250 ms) is logged, with the holder's thread, its raise site (`irql_holder_add` already records it), its kernel call count and the pending vectors, and logged again every second while it lasts; the interrupt waits. Concurrent delivery would reinstate the race exactly when the holder is longest, which is when a list edit is most likely in flight. The vblank costs nothing to withhold: its DPC cannot run while the gate is held anyway, and the schedule and counter keep running. `irq_safe_force=1` (debug) restores delivery alongside the holder after `irq_safe_ms`, for a title that turns out to spin at DISPATCH on something only an ISR does; each such log line is a `spin_waits.json` candidate or a real bug. `irq_safe_points=0` restores today's behaviour entirely.
7. **Vblank bookkeeping.** The tick sets the two interrupt bits and `g_vbl_tick_busy` as now, then posts when the gate is busy. `tick_busy` stays up until the posted ISR returns, since until then PCRTC_INTR_0's bit is the vblank, not an ack; the ack watch is armed at the post (as for a declined vblank today, so the DPC's ack is seen whenever it comes); the claimed and declined counts move to the delivery. A second tick while the bit is pending coalesces: the counter advances, the ISR runs once. Only the guest ISR call moves; `xbox_VblankAckWait` is already asynchronous.
8. **APU and OHCI.** The APU frame thread posts and goes on with its frame, so the FE-trapped handshake with a DPC holding the gate cannot deadlock. The routine on the holder reads APU registers through the MMIO trap, which takes `d->lock` as any guest access does; the frame thread drops the lock once per frame, as it must for the title's voice calls. `apu_irq_stats` gains `posted` and `holder_delivered`; `forced` stays for the opt-in. OHCI's 200-repeats watchdog counts deliveries, not posts. Both models' hold-off counters go away under the new path.
9. **DPC ordering.** A routine delivered on the holder queues its DPC through `KeInsertQueueDpc` as now; the timer thread drains it once the gate is free, or in the same drain when the holder is the timer thread, as a DPC queued by a hardware ISR runs when the processor drops below DISPATCH.

## Deadlock review

- *Holder blocked in a host wait inside a thunk* (an event wait at DISPATCH, a lock in a device model): it reaches no safe point until the wait ends. Today's forced delivery would land then; now the interrupt waits and the log names the holder. If the wait is for something the ISR does, that is the `irq_safe_force` case and a bug report.
- *Holder spinning in pure guest code*: the same; the fix is a `spin_waits.json` entry (a safe point), named by the log.
- *Reentrancy*: a safe point in a kernel thunk that holds a host lock cannot deadlock, because the hook runs at thunk entry before any lock; the gate-release hook runs after the DPC or routine returned, holding only the gate, which is recursive.
- *Routine on the holder takes the gate*: recursive section, no self-wait.
- *Delivery at the wrong IRQL*: the holder is at DISPATCH (gate through a raise or a DPC) or at PASSIVE with the gate (KeSynchronizeExecution); the routine runs at 16 either way and the holder's level is restored. A routine that returns at another level is put back by `xbox_IrqlLeaveInterrupt`, as today.
- *Lost post*: closed by the second TryEnter (decision 4). A post while the holder is already inside the gate-release hook is seen by that hook's loop or by the deliverer's second try, never by nobody.
- *Nested interrupts*: `in_isr` keeps a routine's own kernel calls from delivering; same-vector repeats coalesce.
- *Worker stack exhaustion*: the bit stays pending; logged once.

## Test

`tests/irq_safe_points` (standalone, POSIX and Windows), against the real gate, `xbox_IrqPost` and `xbox_IrqSafePoint` from the runtime library, with two host threads and events for every hand-off, so each case is deterministic rather than a race run many times:

- *Race shown*: the holder takes the gate, starts a two-step edit of a shared doubly linked list and parks on an event mid-edit (canary set). The other thread posts a routine that edits the list. With `irq_safe_points=0` the routine runs at once and sees the canary; the test records that, and that is the bug. With the change, the routine has not run when the holder resumes, and runs inside the holder's next safe point call, on the holder's thread, with the canary clear.
- *Gate release*: the holder lowers IRQL with a post pending: the routine runs before the gate is free (the other thread's TryEnter during the routine fails).
- *Non-holder*: a third thread at PASSIVE calls a safe point with a post pending and runs nothing.
- *Registers and IRQL*: the holder sets a pattern in the TLS registers before the safe point; the routine clobbers them and asserts level 16; after the safe point the pattern and the level are back.
- *Nesting*: the routine calls a safe point with a second vector pending; it does not run inside the routine and runs after it.
- *Coalescing*: three posts of one vector, one run.
- *Lost-post window*: the holder releases between the deliverer's first TryEnter and its post (events order it); the deliverer's second try delivers.
- *Wait and log*: a holder that never reaches a safe point for 2 x `irq_safe_ms` (set to 20 ms for the test) produces the log line and no delivery; with `irq_safe_force=1` it delivers after `irq_safe_ms`.
- *Stress*: 100k rounds of edits with safe points between them, random posts, list intact at the end.

## Risks

- **Latency.** An interrupt waits for the holder's next safe point. DSOUND, D3D and XAPI code at DISPATCH calls the kernel often, but a long pure-guest DISPATCH section delays audio and the vblank ISR by its length. The `[IRQ]` summary reports the longest wait per vector, and `audio_check.py` on the stage1 run catches an underrun.
- **MMIO poll loops.** A holder's register loop that waited for an interrupt's side effect used to get it by the forced delivery; now it waits until the loop exits or is lowered. The log makes it a one-line config fix.
- **Behaviour change for every title.** Gates: BLiNX 2 goldens on Metal and D3D11, Burnout 3 boot and audio under Proton on the exact head, and the mission-1 results repro.
- **Upstream fit.** Upstream's README records the bounded hold-off as its answer to USB interrupts landing in XAPI's half-built pipe setup (#90, #91, #96) and holds #128 for changing threading, IRQL and APU behaviour for every title at once. This change keeps the hold-off's guarantee (an interrupt never lands inside a DISPATCH section) and removes its bound, which is the part that was wrong; it belongs to the one-CPU gate PR cluster, as one small commit with the DSOUND evidence, under `analysis/upstream/pr-stack-plan.md`. Verdict to confirm in the Fable review: argue upstream.
