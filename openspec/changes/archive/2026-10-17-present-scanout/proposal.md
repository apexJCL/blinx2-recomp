## Why

Burnout 3's race-start card jitters on every build with a scaling present (investigation in `runs/b3jitter/REPORT.md`). For the ~180 flips of the card the executor's present pick alternates between 640x480 and 640x464 flip by flip; both GPU backends crop the frame to that size (`present_extent`) and aspect-fit it (`nv2a_present_rect`), so on a 1280x800 fullscreen the picture is 1103 px wide on one flip and 1067 on the next, a 20 px jump at each edge at 60 Hz. The guest content is the same on both flips (rows 16-463); only the size the pick reports moves. It is visible under `present.fullscreen`, `present.filter = linear|integer`, `render.scale > 1`, `present.surface = internal` (the default in Game Mode since toolkit 1b01131), a resized window, and on Metal in every mode, since the drawable is always aspect-fitted. At stock (an unresized 640x480 window, nearest, scale 1) the frame is copied unscaled and the alternation is invisible, which is why it was never seen before the enhancements layer reached b3 (37204d3). It is not a regression of any recent toolkit change (GOOD 72e5429, BASE 6c06ae4 and BAD f966450 all alternate).

The cause is bookkeeping, not rendering (`present_pick()` and `present_note()`, `src/kernel/nv2a_pb_exec.c`):

1. B3 double-buffers 0x005E8000 and 0x00714000 through pushbuffer flips, while `xbox_GetDisplayFramebuffer()` stays at the AvSetDisplayMode address 0x005E8000 (mode 0x080F0D12, pitch 2560). The size scan (pass 0) therefore looks only at 0x005E8000's entries.
2. Each back buffer is recorded at three clip sizes per frame (640x480 for the speed-blur composite, 640x464 for the scene and HUD, 640x463 for the card text), and the frame also touches 13 offscreen targets. The card needs 19 entries; `s_psurf` has `PRESENT_MAX` 16 and evicts by LRU. A frame into 0x00714000 evicts 0x005E8000's 640x480 entry (the oldest), so the next pick finds 640x464 there; a frame into 0x005E8000 recreates it, so the pick after that is 640x480 again. When the card ends the 463 clip goes, 16 fit, and the pick is stable.

The CRTC has no such table: it scans out whichever buffer `PCRTC_START` names, at the display mode's size, and a title's clip rectangles never reach it. Our pick models that with the clip extents it sees, and the model breaks when it forgets a scanout buffer.

## What Changes

- **A scanout set in the executor** (design D2): a small ring of the offsets the last `present_stale` flips presented, cleared on a display-mode change. The size scan accepts an entry at the display address or at any scanout offset, so both of a double-buffered title's buffers set the size, and the one at the display address no longer has to carry every size alone.
- **Eviction spares scanout entries, `PRESENT_MAX` 32** (design D3): when `s_psurf` is full, the LRU victim is taken from the entries that are not at a scanout offset (or the display address) first; only when every entry is one of those does plain LRU apply. The table doubles, so a frame that touches 19 surfaces no longer evicts at all; the protection is what makes the fix hold for a title with more offscreen targets than that.
- **Nothing else in the pick moves**: size first, then the newest draw since the last flip, then the newest clear; the staleness window; the field-pitch fallback; the physical-address compare; the display-mode generation. Every existing `nv2a_backend_smoke` present case keeps its expectation.
- **A CPU-path test** in `tests/nv2a_backend_smoke` (design D5): the B3 pattern (display at A, back buffers A and B, three clip sizes and 19 offscreen targets a frame) presents 640x480 on eight consecutive flips; a mode change clears the set; a single-buffered title with too many targets keeps its size; a table full of scanout entries still evicts. The first and third fail on the base and pass with the change.
- **Recommended, with reasons (design D1): phase 1 is this change; phase 2, presenting the display mode's own height, is a separate change if the user wants it.** Phase 1 removes the per-flip jitter with no new facts about the hardware or the kernel and no change to any tested present behaviour. Phase 2 would also remove the one remaining size change, menus at 640x464 to the race at 640x480 (TASKS follow-up (f)), but the kernel records no display height today (the AvSetDisplayMode mode word is a kernel table selector), it needs a decision on field rendering and on the 320x240-of-a-640x480-target crop that `metal-present-mirror` specified and tests, and it is not needed to fix the tracker item.
- **Out of scope:** the menu-to-race size change (phase 2, TASKS (f)); interleaving fields; the choice among same-size candidates (the newest-draw rule stays; see D2 for the one case the B3 trace should confirm); any backend change (both read the executor's pick; D6).

## Impact

- **Backends:** D3D11, Metal and the CPU path all take the frame's size from `nv2a_pb_present_state()`; the change is in the executor only and no backend file changes (design D6). At stock nothing visible changes for BLiNX 2; for Burnout 3 the stock copy of a race frame now covers rows 464-479 from the guest buffer on every flip, as the hardware shows them, instead of a black band on half the flips (design D4).
- **Hosts:** Mac (Metal, headless), the Deck under Proton standing in for the Linux/Proton host (D3D11, Mac-built exe; memory note *deck-proton-bench*).
- **Goldens:** attract, stage1 and story must pass unchanged on Metal and D3D11, and every flip of each scenario (`RECOMP_FLIP_LOG`'s `presents 0x… WxH`) must be a back buffer at 640x480, as on main (design D4). No reference is re-recorded.
- **Toolkit:** yes, `src/kernel/nv2a_pb_exec.c` and `tests/nv2a_backend_smoke/smoke.c`, on a branch off `posix-host/portability`. Title-neutral (the present pick is one of the fork's walker features, `0d0ad42`), so it is an upstream candidate with that series and not on its own.
- **cat:** `docs/env.md` rows for `present_stale` (the window now also bounds the scanout set) and `RECOMP_PRESENT_TRACE` (it prints the set); TASKS. No new key.
- **b3:** nothing in the repo; the race gate runs from a b3 build against the branch.
- **Overlap:** `feat/fork-prs-aniso-bumpenv` (likely to merge first) touches `nv2a_pb_exec.c` only at `vsh_method` (`SET_SHADER_OTHER_STAGE_INPUT`) and `nv2a_pb_state.h` only in `struct nv2a_pb_vsh`; the present block (lines 779-1038) and `struct nv2a_pb_present` are untouched, and its tests are not `nv2a_backend_smoke`. A clean rebase either way (design D7).
- **Needs the user:** whether to commission phase 2 now or leave it as TASKS follow-up (f) after phase 1 is measured (the recommendation is the latter); the Deck for the fullscreen race run.
