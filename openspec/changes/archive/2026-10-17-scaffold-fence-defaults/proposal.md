## Why

Spartan: Total Warrior was scaffolded with `xbr new` and, to boot past D3D device creation (change `spartan-semaphore-ctxdma`), needed three lines added to its `src/main.c` by hand (`runs/spartan/20261015-001139-ITEM-mac/main.c.diff`; the result is `spartan/tca/src/main.c` 717-749):

- `RECOMP_VBLANK` defaulting to `"1"` when the environment does not set it;
- `RECOMP_TITLE_KEVENTS` defaulting to `"1"` the same way;
- `xbox_Nv2aMirrorFence(0x235528, 0x2C, 0x30)`.

BLiNX 2 (`cat/src/main.c` 1146-1163) and Burnout 3 (`b3/src/game/main.c` 962, 1087) carry the same three. Apart from the constants `xbr new` patches in, those two blocks are the whole difference between Spartan's `main.c` and the toolkit's template (`diff templates/new-game/src/main.c spartan/tca/src/main.c`: hunks 2, 28-31, 106-108 and 689 are the CLI's patches; 716a717-732 and 717a734-749 are the hand edits). So a third title found the same three gaps a second and a third title had, and the template still ships all three open.

**Why every XDK D3D title needs the two keys.** XDK D3D8 connects the NV2A interrupt and paces `Swap`, `BlockUntilVerticalBlank` and the title's vblank callback on the vblank DPC, and it builds the KEVENT that DPC sets by writing the header inline, without `KeInitializeEvent`. The toolkit raises vblanks only when `RECOMP_VBLANK` is set and gives an inline KEVENT a host event only when `RECOMP_TITLE_KEVENTS=1` (upstream's `ke_guest_event`, opt-in there). The Spartan runs show what each gap does on a POSIX host: with neither, the vblank DPC's `KeSetEvent` faults (`runs/ITEM/r6-proto`, SIGSEGV); with kevents only, the boot stops in D3D's vblank wait `sub_00226790` (`runs/ITEM/r8-proto-kevents-only`); with both, it goes on to the wait-for-idle (`r9`). The CLI's `docs/porting.md` already tells the porter to try `RECOMP_TITLE_KEVENTS=1` and then make it the game's default in `main.c`; the template should carry both defaults so the porter never meets those two stops.

**Why the mirror line cannot be a plain default, and how it can be found.** The device pointer is per game, so the template cannot carry a value. But the function it is for, D3D's fence wait, is the same library code in every title seen: its first instructions are `push esi; mov esi, [D3D__pDevice]; mov eax, [esi+0x30]; mov ecx, [eax]; mov eax, [esi+0x2C]; mov edx, eax; sub edx, ecx`. A scan of the three dumps' `D3D` sections for that instruction sequence, with the pointer as the one wildcard, finds it exactly once in each: BLiNX 2 `0x002E8110` → `0x2F1FB8` (D3D8 1.0.5849), Spartan `0x00228FA0` → `0x235528` (D3D8 1.0.5849), Burnout 3 `0x00351770` → `0x35FB48` (D3D8LTCG 1.0.5849, whose build moves the fence argument into `edi` between the pointer load and the field reads). The two field displacements, `+0x30` and `+0x2C`, are in the same bytes. That is cheap enough for `xbr new` to do when it reads the dump, so a new scaffold can carry the live line and the porter only has to confirm it from the runtime's log.

**The deferred 0x400B10 fallback.** Design D3 of `spartan-semaphore-ctxdma` decided that PGRAPH `0x400B10` keeps following the fence mirror and fixed the shape of a fallback for the title that registers no mirror: the register follows the executor's last semaphore release only when `g_fence_mirror_count == 0` and the executor has released at least once, never overrides a registered mirror, logs once, and gets its own branch, ctest and three-title runs. That work was deferred to this change.

## What Changes

- **Toolkit, the template (`templates/new-game/src/main.c`; design D1 and D2):** after the memory layout is mapped and before the kernel starts, the two defaults as `cat/src/main.c` has them, with comments that say why (the XDK D3D builds its own events; its vblank waits), and a fence block whose last line is the commented example `/* xbox_Nv2aMirrorFence(0x00000000, 0x2C, 0x30); */` with the three titles' pointers and the field layout in the comment. The `template_main` ctest gains a text check that the two defaults and the example line are in the template.
- **CLI (`xboxrecomp-cli`, design D2):** `xbr new` reads the dump's `D3D` section when it reads the header, looks for D3D's fence wait, and when it finds exactly one match replaces the example line with the live `xbox_Nv2aMirrorFence(<pointer>, <put>, <get>)` line; otherwise the example stays and the summary says why. The summary also names the XDK libraries the dump links (`D3D8 1.0.5849`). `docs/porting.md` gets a section, "The D3D fence", on what the line is, how `new` finds it, and how to find it by hand. Version 0.7.1.
- **Toolkit, the runtime (design D3):** `fence_completed()` in `xbox_memory_layout.c` falls back to the executor's last released value when no fence mirror is registered and the executor has released at least once, with one log line; the PGRAPH tick is exported so a ctest, `tests/pgraph_fence`, can drive it. `kernel_vblank_enabled()` reads `RECOMP_VBLANK` with `recomp_env_on`, so `=0` turns vblanks off once the template defaults them on.
- **Spartan, as the test:** a fresh `xbr new` scaffold of Spartan, with no hand edit to `src/main.c`, boots to the stop the tracker item recorded (the `KeDelayExecutionThread` poll under `sub_001ADCA0`) on the Mac and on the Deck. The same scaffold with the fence line commented out boots to the same stop through the fallback.

## Not in this change

- **Toolkit runtime defaults for `RECOMP_VBLANK` and `RECOMP_TITLE_KEVENTS`.** Decided in design D1: they stay per-game lines, carried by the template. The vblank "auto" idea (raise vblanks once the title has connected the NV2A interrupt and enabled it in `PCRTC_INTR_EN_0`, which is what the hardware does) is recorded there as future work for the toolkit and an upstream conversation, not done here.
- **The runtime finding the device pointer itself** (scanning the loaded image at boot and registering the mirror). The line belongs in the file the porter reads, with the comment that says what it is and how it was found, and the mirror is a deviation the fork wants to retire, not spread silently (design D2).
- **Signatures for other XDK versions.** The three dumps are all XDK 5849 (D3D8 and D3D8LTCG). The detection never guesses: zero or several matches is "not found", the example line stays, and the porter follows `porting.md`. A fourth title on another XDK adds its signature when it is seen.
- **Retiring the fence mirror.** The fallback narrows what the mirror is needed for (with it, a title with no mirror passes both D3D's fence wait and its wait-for-idle through the executor alone), but the mirror is still the catch-up path when a walk stops short of PUT and the only fence with `RECOMP_PB_EXEC=0`. The `deviations` entry stays; the register entry is rewritten (specs).
- **Re-scaffolding `spartan/tca`.** It already carries the three lines; its `[cli]` pin moves to the release that carries this change in the next push round (the tracker item's open task 2.6 says the same).
- **A `BLX-[0-9]+` pattern in the CLI's `scripts/audit-public.sh`.** That is the tracker item's open task 4.5. The gate here is a `git grep` for tracker ids on the CLI branch.
- **Other main.c conveniences the three titles share** (the guest lock, `RECOMP_PB_BACKEND=metal`, which the template already has). The guest lock is BLiNX 2's own finding, not shown on another title; it stays out.

## Impact

- **New scaffolds:** a title made by `xbr new` with a readable dump starts with the two defaults and, on an XDK 5849 D3D, the live mirror line. The porting loop's first POSIX stop (`porting.md`'s "The first title-specific fault") goes away for those titles.
- **BLiNX 2, Burnout 3 and Spartan:** no behaviour change. All three register a mirror, so the fallback never engages for them (design D3 states the condition and the ctest pins it); the template is not re-applied to an existing game; `RECOMP_VBLANK=0` was never set by any bench, golden or launcher (`cat/docs/env.md` lists no `=0` for it), so the `recomp_env_on` change is a no-op for every recorded run. The toolkit runtime branch still runs the CLAUDE.md gates for a runtime change (tasks 3.6 to 3.8); the template branch changes no runtime code and needs none.
- **Hosts:** the fallback is in the shared ack loop, so D3D11, Metal and the CPU backend see the same register. The template is the two-host template; the new block is host-independent and sits in the shared `host_main`.
- **Public repos:** the CLI release (0.7.1) and the toolkit commit carrying the new template both go out in the next push round, the toolkit's first: `xbr new` pins the public `blinx2/portability` tip, so a public scaffold only gets the new template once that branch has it. Against an older template the CLI degrades to a note (design D2), never an error. No game data is involved: the detection reads the porter's own dump on the porter's machine, and the spec's three pointers are addresses, not content.
