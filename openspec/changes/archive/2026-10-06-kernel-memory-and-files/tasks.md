- [x] 1.13 FATX overwrite semantics on POSIX (`ea3d2f7`, `8773d89`). The texture-cache copy (sub_001B8140, then sub_001B8240) writes `x.tmp` padded to 512 bytes, reopens it with CREATE_ALWAYS, and only sets the end of file to the true size. - [x] 1.15 SIGSEGV at sub_002D8294+0x1F0 as stage loader #7 exits, about 260 s into a cold attract run (`esi=0xFF59A059`). Cause: the CRT reads its per-thread pointer at `[fs:[4] + index*4]`, and the title computes the index as -37 from its `.rdata` TLS directory (0x90 bytes of zero fill, so a 0x94-byte block). The loader sized TLS from the XBE header's copy of that directory, which BLiNX 2 leaves zeroed: a 4-byte block with fs:[4] 4 bytes past it. The CRT therefore read 0x90 bytes below the block. On threads #5 and #6 that read zeros, and the exit path silently cleared guest address 0xC. On loader #7 it read texture bytes from the heap block next to its TIB, and the write faulted. Fix (`56a5062`): PsCreateSystemThreadEx honours TlsDataSize as the Xbox kernel does. KTHREAD.TlsData (+0x28 of the thread object, which fs:[0x28] now names) gets that many bytes at the top of the worker's stack, and fs:[4] points just past them. The main thread takes its block from the heap. Cold 420 s runs, with and without `RECOMP_PB_EXEC=1`, have every loader exit with no fault. After the demo, the attract loop now returns to the title screen (`analysis/bringup/kmem-tls-title-again-f036.png` (local analysis, not published), from about 290 s). That screen is drawn at 0x00811000, and the frame dump decodes it at the wrong pitch. The guest heap is now also locked (`55ab7d8`); that lock was a candidate cause that the trace ruled out. `RECOMP_HEAP_TRACE=<va>` logs each owner of a heap block.
