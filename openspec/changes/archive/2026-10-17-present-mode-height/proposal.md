## Why

Phase 1 of the tracker item (`present-scanout`) stops the executor's present pick alternating between two clip extents of the same buffer. It leaves the extent itself as the title's clip: Burnout 3's menus are 640x464 and its races 640x480, so each menu-to-race and race-to-menu transition is still a 3.4% size step under any scaling present (TASKS follow-up (f)). The user chose to close that too (2026-10-15).

The console does not have the problem because the CRTC never sees a clip rectangle. AvSetDisplayMode programs the encoder and CRTC for one timing, and from then on the CRTC scans `PCRTC_START` at that timing's width and active lines: 480 of them for every mode either title uses, whatever rows the title drew. A title's 640x464 menu is a 640x480 frame on the TV with sixteen rows of whatever is in the buffer, and the picture never moves. xemu shows the same thing: its framebuffer surface is sized from the VGA CRTC state the kernel programmed for the mode, with the address from `PCRTC_START`.

The runtime cannot do that today because nothing records the display's size. The kernel bridge keeps the resolved framebuffer address, the pitch and a generation (`xbox_SetDisplayFramebuffer`, `xbox_DisplayModeBump`); `xbox_AvSetDisplayMode` stores the mode word only for `AvSendTVEncoderOption(AV_OPTION_QUERY_MODE)`; the walker, the CPU presenter, the Win32 window and the checksum probe each assume 480 or take the clip. Design D1 finds the size: the XDK's D3D carries a display-mode table (180 rows, byte-identical in BLiNX 2 and Burnout 3) that maps each AV mode word to one width and height, and the word's timing byte alone determines them; the mode words are the kernel's own vocabulary (nxdk publishes the same words with the same sizes). Field rendering is not in the word: the same word serves a title's 640x480 frame and its 640x240 field buffers, and D3D tells the kernel about fields only by halving the pitch it reports, which is exactly what the present code already detects.

## What Changes

- **The kernel records the display mode's size** (design D1, D2): `AvSetDisplayMode` resolves the mode word to `(width, height)` through a table of the kernel's AV timings held in `kernel_hal.c`, and stores it beside the address, pitch and format, before the generation bump. An unknown word records no size (one log line), and everything then behaves as phase 1. The CPU presenter's and the probe's hard-coded 480 read the record.
- **The present extent is the display's size** (design D3): after phase 1's pick of *which* surface the flip shows, the extent it reports is the display's `(width, height)` when the surface is at the display pitch, and `(width, height / 2)` when it is at twice the pitch (field rendering, one field, as today). A surface at any other pitch, a run without a display mode, and an unknown mode word keep the clip extent.
- **The crop rule is narrowed, not overturned** (design D4): the fresh-clip crop of `metal-present-mirror` and D3D11's 4bfee1c stays the rule without a display mode and is exactly what the smoke's crop case pins; with a display mode the frame is the display's size. The reason behind the crop (a host target grown past the frame must not show its margin) is kept by construction, since the extent never exceeds the display.
- **Both GPU backends grow a target the extent exceeds** instead of clamping to it (design D5), through each backend's existing `rt_grow`, so Metal, D3D11 and the CPU path show the same rows. For BLiNX 2 and Burnout 3 that path never runs: their back-buffer targets are made at 640x480 by the first clear.
- **Tests:** a kernel ctest for the table and the record; smoke cases for the narrowed crop with and without a mode, a field title, a mode change to 720p, an unknown word and the B3 menu-then-race pattern (design D6).
- **Out of scope:** interleaving fields into one frame (a follow-up: on the console both fields sit in alternate rows of one 480-line frame, so a field title could be shown whole from guest memory); the mode word's widescreen bit as an input to `display.aspect`; PAL modes beyond carrying them in the table (the runtime reports NTSC-M).

## Impact

- **Backends:** the executor (extent), both GPU backends (`present_extent` grows instead of clamps; D3D11's `internal_resize` follows), the CPU presenter and the Win32 window (size from the record). At stock, BLiNX 2 is byte-identical (design D7); Burnout 3's menus are copied at 640x480 instead of 640x464, with rows 464-479 from the guest buffer, which is what the console shows. No title-specific code.
- **Hosts:** Mac (Metal, headless), the Deck under Proton standing in for the Linux/Proton host (D3D11, Mac-built exe).
- **Goldens:** attract, stage1 and story unchanged on Metal and D3D11; the per-flip present sequence identical to main's (BLiNX 2 presents 640x480 from the display address throughout, and 640x480 is its mode's size). No re-record. Burnout 3 has no golden; the race gate's checks (race reached, FPS, audio, stock `[ENHANCE]` lines) do not compare frame sizes, so nothing there is re-recorded either (design D7).
- **Toolkit:** yes, title-neutral: `src/kernel/kernel_hal.c` (table), `kernel_bridge.c` and `xbox_memory_layout.c` (record), `nv2a_pb_exec.c` (extent), the two backends' `present_extent`, `fb_present.c`, tests. Upstream candidate with the walker-present series, after phase 1.
- **cat:** `docs/env.md` (the `present_stale` and `RECOMP_PRESENT_TRACE` rows mention the display size; no new key), TASKS (closes follow-up (f)).
- **Stacking:** the toolkit branch is cut from `fix/present-scanout`'s tip and lands after phase 1's squash, rebased onto `posix-host/portability` then (design D8). `feat/fork-prs-aniso-bumpenv` touches none of these files' regions.
- **Needs the user:** the Deck for the fullscreen menu-to-race run; a decision only if design D1's table disagrees with a title's pitch at runtime, which the one-time log would show and which no run so far suggests.
