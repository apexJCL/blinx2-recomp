## Why

BLiNX 2 hangs again in mission 1 on macOS (cat a9a4845 / toolkit a0b9a55): open the door with bombs instead of the key and the game freezes at or before the results screen. The live process (PID 76337, read-only lldb, `runs/m1hang/findings.md`) shows the same shape irq-safe-points fixed on 2026-10-06: the kernel timer thread never leaves the DSOUND DPC `sub_003346BE`, because the stopped-voice list at dsound+0x4A0 has a head that points at a node (voice 0x047B4244 + 0x54) which points at itself. `RemoveEntryList` on that node is a no-op, so the drain loop runs forever at DISPATCH holding the one-CPU gate; the workers block in `KfRaiseIrql`, guest-main spins in `sub_0005F960`, the APU line stays posted and audio stops.

The runtime's own counters, read from the live process, say the interrupt race is gone: `forced 0/0/0`, `ungated 0/0/0`, safe points on, nothing forced. Both deliveries of the DSOUND interrupt were serialized. What remains is the second half of the console's contract, which irq-safe-points left to the timer thread (its design item 9): **a DPC queued by an ISR runs before any thread resumes at passive level**. On the Xbox, `KeInsertQueueDpc` from the interrupt handler runs the routine on the interrupt's exit path, when the processor drops below DISPATCH, before the interrupted thread gets the CPU back. DirectSound counts on it: its ISR appends the idle voice to the stopped list without a linked check, because by the time the title can call Play on that voice again the DPC has drained the list and taken the voice off the hardware list.

Here `bridge_KeInsertQueueDpc` only appends to `g_dpc_queue`. Nothing wakes the timer thread; `kernel_timer_loop_ns` sleeps to the next vblank edge, timer or a 10 ms cap, and `kernel_drain_dpcs` only tries the gate, leaving DPCs "queued for the next tick" (1 ms later) whenever a title thread is at DISPATCH, which every DirectSound API call is. So an ISR-queued DPC runs 0 to 10 ms later, and in that window the title's threads run freely. The APU model re-traps an idle voice every 5.33 ms frame while it is still on the hardware voice list (`apu_vp.c`, `SE2FE_IDLE_VOICE`), and the DPC is what removes it. The sequence: ISR#1 queues the stopped voice and the DPC; the title re-triggers the sound (bombs: Play re-links voice+0x4C and re-allocates the same hardware handle); the next frame traps the same handle again, ISR#2 passes every guard and inserts the voice a second time; the DPC then runs forever. The bomb door adds no new path; any sound re-triggered within the window can do it, on the Deck as well as on the Mac, with host timing deciding how often.

## What Changes

- **DPCs run on the thread that lowers the processor below DISPATCH, as on the console.** A guest thread (guest-main or a spawned worker) that raises to DISPATCH_LEVEL (`KfRaiseIrql`, `KeRaiseIrqlToDpcLevel`) and finds DPCs queued runs them right there, at DISPATCH, holding the gate it just took, before its own critical region begins; and a guest thread whose lower gives the gate back runs what is queued at the release point, after the posted interrupts. The routine runs on the thread's own guest stack with its guest registers saved and restored, the way posted interrupts run at safe points. This closes the window where DirectSound needs it: every DirectSound entry raises IRQL first, so Play cannot run before the stop DPC has drained.
- **Device-model threads never run DPCs.** The APU frame thread and the OHCI controller thread deliver interrupts under the gate but leave the queue to the next guest raise or the timer thread: the DSOUND DPC can wait on the frame thread to clear a trapped front-end method (Burnout 3's vehicle select froze on that pair once).
- **`KeInsertQueueDpc` wakes the timer thread.** The nanosecond timer loop sleeps on a wakeable wait; a queued DPC ends the sleep, so the plain path (no guest thread raising) drains in microseconds instead of up to 10 ms. The busy-gate retry stays at 1 ms: a guest holder now drains at its own release, so the retry only covers a device-model holder's short gated delivery.
- `RECOMP_DEBUG=dpc_on_raise=0` restores the timer-thread-only drain (A/B), with a row in `docs/env.md`.
- No change to generated code. A linked check in `sub_00335C18` would mask this instance only and is a hand-edit.

## Capabilities

### Modified Capabilities
- `kernel-threads`: DPCs queued by an interrupt run before guest code resumes below DISPATCH: on the next guest raise, at the gate's release, or on the woken timer thread; never on a device-model thread.
