## Why

The Xbox runs a title's threads on one CPU with a strict priority scheduler: the highest-priority ready thread runs, a thread made ready at a higher priority preempts the running one at once, and threads of equal priority take turns at the quantum. Titles build on that. CRI's ADX middleware, used by JSRF and BLiNX 2, protects its server with a "priority lock": the lock (JSRF `sub_0013B0A0`, BLiNX 2 `sub_002ACBA0`) saves the caller's priority, raises it to 15 (time critical) and resumes a helper thread; the unlock (`sub_0013B0E0`, `sub_002ACBB0`) suspends the helper and restores the priority. Nothing else excludes the other threads: at 15, no title thread can run until the holder drops back, so the critical section is atomic. JSRF's wait helper `sub_001437B0` even reads `GetThreadPriority(-2) == 15` to ask "am I inside the lock".

The runtime does not keep that guarantee. With `RECOMP_GUEST_LOCK=1` guest code runs on one host thread at a time, but the guest CPU goes to waiters in ticket order, at the quantum (4 ms), at every kernel call and at spin-wait passes, whatever the priorities. The host priorities toolkit b7e82411 applies cannot help under the lock (review, finding 1): a host priority decides which host thread the OS runs, not which guest thread holds the guest CPU, so it is off when the lock is on, and the priority query returns 0. So the ADX server can be preempted inside its lock by a lower-priority title thread, and `sub_001437B0` never sees 15. The review (finding 4) names the faithful fix: a guest CPU that knows priorities.

## What Changes

- **The toolkit keeps each guest thread's base priority** (the `KeSetBasePriorityThread` increment, NT's ±16 saturation to 15 and 1) in a per-thread record next to the guest CPU lock. While the feature is on, `KeQueryBasePriorityThread` returns the stored value and `KeSetBasePriorityThread` stores it; host thread priorities are left alone.
- **The guest CPU orders its waiters by priority.** A release goes to the highest-priority waiter, oldest first among equals, so equal priorities keep today's FIFO and round robin.
- **A holder that outranks every waiter keeps the CPU** at the quantum, at back edges, at spin-wait passes and at `NtYieldExecution`. A higher-priority waiter asks the holder to give way at its next back edge, the closest the runtime comes to the console's immediate preemption.
- **A kernel call's soft release** (the holder gives the CPU up for the length of the call) goes only to a waiter at the caller's level or above while the call is short; anyone may run once the caller blocks, as on the console. A sleep or file I/O blocks at once; a wait or a contended critical section only when its bridge finds it must block (a wait on a signalled object returns without a switch on the console); any other call is taken as blocked past 2 ms, and those admissions are counted and, under a time-critical holder, named.
- **Suspend and resume of another guest thread are counted guest-side.** A suspended guest thread is skipped by the guest CPU and gives it up at its next back edge. On POSIX `SuspendThread` of another thread only counts today, so JSRF's spinner thread `sub_0013B180` (resumed by the ADX lock at priority +2, it loops on a back edge with no kernel call) would never stop and would starve the title threads once priorities count.
- **Opt-in:** `RECOMP_DEBUG=guest_sched=1`, a debug-tier key, default OFF. It works only with the guest CPU lock on and `guest_priority` not 0. Off, the runtime behaves as before (a few hooks run but change nothing; design D1).
- **Diagnostics:** a `[GUEST]` line when a waiter has waited more than 1 s (rate limited, naming the holder's last site), a line at each new longest wait from 50 ms, and in the pacing report the hand-offs refused for priority, the admissions past 2 ms and the valve firings.
- **A hang guard:** a waiter kept off 4 s gets one turn and a loud line (design D7). It exists only for model gaps; a golden wants 0 firings.
- **Out of scope:** dynamic priorities other than the +1 wake boost modelled for a thread back from a block (`KeSetPriorityThread`, the dynamic priority, keeps its existing path), the suspend-count limit (127, `STATUS_SUSPEND_COUNT_EXCEEDED`), priority inheritance, interrupt and DPC ordering (they run outside the guest CPU), and making the feature the default. That needs the gates in tasks §4 and a later change.

## Impact

- **Toolkit:** `src/kernel/kernel_guest_cpu.c` (the scheduler), `src/kernel/kernel_bridge.c` (priority, suspend and resume bridges; thread object hooks), `src/kernel/kernel_sync.c` (a wait polls before it says it blocks), `src/kernel/kernel.h`, `src/platform/recomp_env.h` (the `GUEST_SCHED` row), and new ctests `tests/guest_sched` and `tests/guest_sched_bridge`.
- **cat:** a `docs/env.md` row for `guest_sched`, this spec and TASKS.
- **Behaviour:** none by default. With the key on, titles that rely on priorities (CRI ADX in JSRF and BLiNX 2) get the console's ordering; a title whose high-priority thread spins without blocking can starve lower ones, as it would on the console.
- **Goldens:** BLiNX 2 Metal goldens with the lock on must pass with the key on and off. Proton, native Windows and Deck runs come before any default change.
